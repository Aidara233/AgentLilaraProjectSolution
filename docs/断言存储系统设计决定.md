## 一、断言的基本结构

采用两层结构,内容层和记录层分开,避免混淆"世界发生了什么"和"我什么时候记下的"。

### 1. 内容层(核心断言)

```
assertion_id
subject      -- 实体ID 或 另一个assertion_id(支持嵌套断言)
predicate    -- 关系/谓词,从固定谓词表中选取
object       -- 实体ID、字面值(literal)、或另一个assertion_id
object_type  -- entity / literal,用于判断是否需要做实体链接
polarity     -- true / false / unknown(真值判断,不表示时效)
strength     -- 可选,-1~1,用于表达态度类断言的方向与强度(替代"喜欢/不喜欢"拆成两个谓词的做法)
```

### 2. 记录层(元数据)

```
assertion_id (外键)
source              -- 来源:对话/工具/用户直接告知
source_utterance_id -- 同一次陈述的分组ID(见"断言同源"章节)
recorded_at         -- 系统记录时间
valid_from           -- 断言自带的生效时间(仅当来源信息本身包含此信息时填写)
valid_until          -- 断言自带的失效时间(同上,详见"过期时间"章节)
confidence           -- 置信度
condition             -- 附加限定条件,自由文本即可,不必强行结构化
```

## 二、谓词(关系)设计原则

- 谓词表应**尽量封闭、克制**,新断言优先匹配已有谓词,匹配不到才新增,新增应有审核/去重步骤。
- **谓词只表达关系类型,不编码正负极性**。"喜欢/不喜欢"不拆成两个谓词,统一用 `喜欢` + `polarity`/`strength` 表达。
- **禁止出现复合谓词**(如"父亲的公司")。遇到"A的B的C"这类嵌套结构,拆成链式多条三元组,通过多跳查询(multi-hop traversal)得到答案,不要硬造复合词。
- 每个谓词需标注 **exclusivity(排他性)**,用于矛盾检测:
  - `multi`:同一主体可对多个对象成立,不检查冲突(如"喜欢")
  - `single`:同一主体的该谓词理论上只能有一个正确取值,新旧object不同即触发矛盾标记(如"性别""父亲")
- **已废弃 `single_current` 这一分类**:最初设想对"当前状态类"谓词(如"工作于")自动认为新断言是对旧断言的更新、静默改写旧断言的 `valid_until`。这个设计被推翻,理由见下一章节。

## 三、时序变化 vs 矛盾:核心决定

### 3.1 不允许系统自动判断"这是更新还是矛盾/口误"

- 系统无法区分"换工作了"和"记错了/口误了",不应赋予任何断言"自动修改另一条断言字段"的权力。
- 例:"2020年A就职于B" 和 "2021年A离职于B" 是**两条完全独立的断言**,互不修改对方。
  - `离职于` 是独立谓词,不是"就职于"的取消操作。
  - 若需要"A在B工作的起止区间",由**查询/推理层**动态拼接两条断言算出,并标记为 `derived`(推导结果),区别于 `stated`(原始陈述)。
  - `就职于` 不应标记为 single —— 因为同一个人对同一家公司可以有多段独立任职记录,真正需要检查的是"同一时间点是否存在互相矛盾的状态",这是查询层基于时间区间做重叠检测的工作,不是写入层的谓词唯一性检查。

### 3.2 什么情况下才允许直接写入 valid_until

只有**同一次陈述本身就明确给出了起止时间**,才可以把 valid_from/valid_until 直接写进该条断言:
  - 例:"张三从2020年到2023年在A公司工作" → 一次陈述,直接填字段,合理。
  - 反例:先说"入职"、后说"离职",分属两条独立陈述 → 不能让后一条静默改写前一条的字段。

### 3.3 valid_until 字段的意义(未被取消,而是收窄)

valid_until 依然有存在价值,但只能通过两种方式写入:
1. **来源本身自带失效时间**(见3.2),属于普通内容字段。
2. **查询/推理层生成的缓存结果**,必须打上 `derived: true` 和 `derived_from: [...]` 标记,可随来源断言的变化被重新计算或作废。

**禁止的路径**:检测到"看起来像更新"的新断言,就自动回填旧断言的 valid_until——这条路径被明确否决。

### 3.4 过期(valid_until 已过)的语义

> "断言过期意味着:我很清楚其在那之后就没那么有价值了,除非特殊情况不然没必要想起来。"

查询时可指定时间范围:
- `within`(默认):只返回当前有效的断言,包括没有任何时间信息的断言(视为一直有效)
- `expired`:只返回已失效的,用于历史/变化类查询
- `all`:不过滤,用于审计/溯源

## 四、矛盾检测机制

- 触发时机:①新断言写入时,与同 subject+predicate 的已有断言比对;②新增"实体等同"边时,连带检查两个实体各自的 single 类谓词是否冲突(这是最容易被漏检的场景——矛盾往往不是来自新知识本身,而是"合并"这个动作暴露出的旧知识冲突)。
- 检测到冲突后**不自动仲裁**,而是挂起并生成一条独立的冲突记录:
  ```
  conflict_id
    ├─ assertion_A / assertion_B
    ├─ predicate
    ├─ status: unresolved
    └─ detected_at
  ```
  交给用户澄清或等待后续信息自然收敛,解决后记录最终采信依据。

## 五、实体等同(跨语境身份关联)

### 5.1 基本设计

- 不预先建立"可能相关"的候选关系网(避免"猜多了变蜘蛛网")。
- 只在**明确得知**时建立显式的等同边:
  ```
  实体A -等同于- 实体B
    source: ...
  ```
- 该边应为**等价关系**:自反、对称、可传递(A=B, B=C ⇒ A=C),查询时做传递闭包处理即可,不必在写入时做路径压缩合并。
- 默认状态:没有显式等同边的两个实体,视为不同个体,不主动判定"未知待定"。
- 是否要主动向用户提问澄清,取决于这个不确定性是否实际影响到当前的决策/回答质量,不应无差别地系统内部瞎猜。

### 5.2 负向等同边

- 同样支持 `A -不等同于- B`,用于**明确排除**误判,防止未来任何自动化关联/模糊匹配逻辑把两个已知不同的实体错误地撮合到一起。

### 5.3 什么情况可以不经过等同边、直接共享同一个 entity_id

**关键结论(重要修正)**:能否直接共享 entity_id,取决于"指代关系当下是否可以被确定消解",而不是简单以"是否同一句话"为界:

- **可以直接消解、共享同一 entity_id 的情况**:语篇层面存在显式、无歧义的共指链——包括同一句话内的共同主语,也包括跨句的代词回指、承前省略主语等(如"我有只猫叫咪咪""他喜欢吃水果""也喜欢吃蔬菜",其中"他"和省略主语都应在抽取阶段直接消解回"咪咪",不建临时实体、不走等同边)。
- **必须走等同边、不能直接判定同一实体的情况**:共指链发生断裂或重新起始——典型例子是"有只猫爱吃饭""有只猫爱睡觉",或跨句重复出现同一个名字但没有语法链接(如分别独立提到"咪咪爱吃A""咪咪爱吃B",不能仅凭同名假定是同一只,因为无法排除重名/两只猫的情况)。
- **被否决的错误结论**:曾一度认为"提到了名字就算确定消解",后被推翻——名字相同只是特征匹配的线索,不是身份证明,重名情况现实中大量存在。

## 六、断言同源(同一次陈述拆出的多条断言)

### 6.1 问题背景

一句话可能拆解成多条断言(如"我弟弟喜欢吃水果和蔬菜"拆成两条),这些断言之间的"共同出身"关系值得记录,用于:
1. 避免置信度被重复计分(同一来源的多条不能当作多个独立证据)
2. 支持批量回溯/撤销(发现原话有误时一次性定位所有派生断言)
3. 保留上下文,便于人工审核/排歧

### 6.2 结构决定:星型拓扑,复用实体-关系模型

> **已取代**：6.2 的"话语节点实体 + 属于边"星型拓扑已被 **9.1 的简单 `utterance_id` 字段**取代（同源分组用字段承担，不建边）。本节保留作演进记录。

- **不采用两两建"同源边"的方式**(会产生 O(n²) 数量的边)。
- 决定:将"一次陈述/话语"本身建模为一个**特殊类型的实体节点**(话语节点),所有从中拆出的断言统一通过"属于"关系连向这一个母节点:
  ```
  断言1 -属于- 话语_U003
  断言2 -属于- 话语_U003
  ```
- 子节点(各条断言)之间禁止互相直接建边;任何试图连接子节点的操作,系统应强制重定向到母节点。
- 这样"同源"关系复用了已有的实体+关系存储结构,不需要发明新的边类型或单独的元数据字段体系。

### 6.3 与实体等同边的本质区别(不可互相套用的原因)

| 关系类型 | 结构 | 是否需要传递闭包 | 是否需要矛盾检测 |
|---|---|---|---|
| 实体等同(=) | 自由图,任意两点建边 | 需要 | 需要 |
| 断言同源(属于同一话语) | 星型,强制连向母节点 | 不需要(母节点即聚合点) | 不需要(纯分组,不涉及真值判断) |

两者解决的问题类型不同(等价关系判断 vs 纯粹分组打包),因此适用不同的结构约束,不能把"实体也套用星型限制"或"同源也套用自由建边"这两种做法互相搬用。

## 七、自动推断机制(inferred edges)

### 7.1 背景

出于"让系统显得机灵一点、减少信息碎片化"的考虑,允许系统在**没有明确证据、仅凭统计/启发式线索**(如"小明总是提起咪咪" → 默认视为同一只猫)的情况下,生成推断性的等同边。

### 7.2 约束条件(最终决定)

1. **必须与 stated(明确得知)信息严格区分标记**:
   ```
   实体A -等同于- 实体B
     edge_type: inferred        -- 区别于 stated
     confidence: 0.7
     basis: "同名+同主人+多次独立提及,无反证"
   ```
2. **inferred 信息天生比 stated 信息低一等**:任何 stated 断言,无论其自身置信度多低,都可以直接否定/推翻一条 inferred 边,不需要经过"挂起等待澄清"的矛盾处理流程,直接判 inferred 败诉。
3. **否定后不删除,标记为 refuted 并保留**,记录否定依据,防止未来同类错误推断被重复提出、重复验证:
   ```
   edge_type: inferred
   status: refuted
   refuted_by: assertion_X
   ```
4. **inferred 信息在下游使用(尤其提供给生成模型)时,必须与 confirmed(stated)信息分区展示**,不能混合成同等确定性的陈述,应明确标注其推断性质与依据,避免下游模型把推测当作既定事实陈述。
5. 优先考虑做成**查询时临时计算**,而非写入时批量扫描、永久固化建边——避免错误推断被持久化后不断被后续新断言叠加、越滚越大、难以拆解。如需缓存高频计算结果,也要保留 inferred 标记与定期复核/过期机制,不享有 stated 边的"永久有效"待遇。

## 八、整体分层小结

```
事实层(stated)  —— 保守、可审计、来源明确、冲突需挂起等待人工/后续澄清
   ↑ 单向可被否定
推理层(inferred) —— 大胆、机灵、地位低、可被任意 stated 信息否决、对外必须标注不确定性
```

核心原则贯穿全篇:**系统不做自动仲裁**,凡是"看起来合理的自动判断"(自动改写 valid_until、自动合并实体、自动断定重名同指等),都应转化为显式、可追溯、可撤销的机制(独立断言 + 派生标记 / 等同边 + inferred 标记),而不是静默发生在数据里。

## 九、设计补充决定(2026-08-01 讨论定稿)

> 以下是对前文的深化与修正。冲突处以本补充为准。

### 9.1 断言字段定稿

**无 polarity、无 confidence 字段。** 否定与可靠性均靠显式结构表达(见 9.2)。

```
subject   { type, index, ref? }
predicate { type, index, ref? }
object    { type, index, ref? }
raw       -- 拼好的整句原文(模型写断言时顺带拼一句,召回时直接返回)
source    -- 谁说的 + 哪条消息/哪条经历(承担引用职责)
utterance_id -- 同源分组(一句话拆多条断言的共同出身,防重复计分)
valid_from / valid_until
recorded_at
strength  -- 可选,-1~1,态度类断言的方向与强度
```

- 槽位 `{type, index}`:index 是模型写入时的**表面词**(不做库内规范化),匹配交给系统
- 匹配处置因 type 而异(见 9.3)
- `raw` 承担"原文召回"——召回时直接返回整句,消费端自带上下文消歧

### 9.2 否定、正确性、可靠性的表达(废除 polarity / confidence)

- **否定用 strength 负数**:`喜欢 + strength=-0.8` = "不喜欢"。strength 只表达态度方向强度,不做事实判断。
- **废除 polarity 字段**:事实层面的成立与否不直接存储。
- **废除 confidence 字段**:可靠性不直接存储。
- **可靠/正确性靠推理链(显式断言)**:
  - 来源型:`小明 / 觉得 / [断言X]` —— "谁说的"结构化,可信度由该来源自身的断言链派生
  - 推理型:`断言X / 依据 / 天文课`、`断言Y / 反驳 / 断言X`
- **印证度(Corroboration)不存储,改为派生计算**:数同一断言(subject+predicate+object 归一后)有多少**独立来源**(按 utterance_id 去重),查询时算,不写数字。
- 原则与文档一致:**系统不做自动仲裁**——置信度是推理结果,固化它即违背原则;靠来源链可审计、可追溯。

### 9.3 索引与三库处置

- 索引 = 表面词,**不做库内规范化键**(不把关键词列表灌进模型)
- 各槽位类型的匹配处置:

  | type | 处置 |
  |---|---|
  | entity | **不匹配、不归并**,只保留 index 作显示/原文返回 |
  | keyword / attribute | 关键词库向量匹配 → 词条 id |
  | literal | 裸值,直接存 |
  | assertion | 引用另一条断言 id(嵌套) |

### 9.4 实体设计(关键决定)

- **写入即唯一实例**:提取时创建的实体,除非明确标定同一,否则**永远只是这一条实体记录**;即使同名也不合并(两只叫咪咪的猫 = 两条实体记录)。
- **合并/等同只靠显式断言**:`实体A = 实体B`(通常来自推断,可被推翻)。不靠字符串匹配、不靠"多次提及"。
- **实体身份 = 记录本身**,不是任何名字/标签。名字只是实体的一个属性/标签。
- 实体**不参与向量归并**。
- 实体需要**创建时的上下文锚**(至少关联消息 id / 来源),作为区分依据。
- 关键词管抽象概念(猫/咖啡/红色),实体管具体个体(咪咪),**两边永不相交**。
- 与文档 5.3 的关系:语篇内显式共指(同一句话/代词回指)可直接消解到同一实体;但**跨句同名只是特征线索,不是身份证明**——强化为"默认不合并"。

### 9.5 谓词清单存储形式

- **关系谓词(relation)**:JSON 配置文件(如 `Storage/Assertion/Predicates.json`),封闭、特权注册,工具 schema enum 直接由此生成。初始清单待定。
- **属性名(attribute)**:数据库表(Keywords 表 role=attribute),开放、后台收敛、参与向量归并。
- 同一槽位两种来源,开放度不同,存储载体不同。
