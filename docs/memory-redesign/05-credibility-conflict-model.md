# 可信度与冲突模型

> 记忆重构计划 · 文件 05
> 状态：**设计定稿（未实现）** — 2026-08-02。当前代码无 Claims 表 / 可信度字段，本模型尚未实现。
> 本文件定义：断言可信度（Credibility）的语义与计算、程度值（strength）、支持/反对边、冲突组、Review 验证流程。

## 一、两个正交的字段

| 字段 | 角色 | 例子 |
|---|---|---|
| **`Credibility`**（可信度，锚点） | 这条断言**本身多可信**。写入者定初值，可被 Review 修改 | 0.4（我不太信它） |
| **`strength`**（程度值） | 态度**方向 + 强度**，或支持边的搬运强度 | `爱 +0.9` vs `喜欢 +0.4`（爱比喜欢深） |
| **`IsInference`**（推断标记） | 等级标记，驱动跨等级碾压 + 召回"推断"标签 | true |

**两者正交，不可混淆**：

> 他说他爱她（`strength` 高 = 爱得深），但他满嘴跑火车（`Credibility` 低 = 这条断言不可信）。

`strength` 是边上的量（态度强度），`Credibility` 是断言自己的量（多可信）。一个"我非常喜欢猫"（strength 0.9）可以是低可信（inferred，我不确定它真成立）。

## 二、可信度语义

### 2.1 初建

**初建可信度由写入者决定**：
- **stated**（明确陈述）：常规 ≈ 1.0
- **inferred**（推断）：等于推断确定度（如 0.4~0.7），只表示推断的确定度

`IsInference=true` 的断言：
- **跨等级被碾压**：任何 stated 断言可直接否定它，与数字无关（等级决定，见 4.4）
- **召回时带"推断"标记**：对外展示必须标注推断性质与依据，不得混同于既定事实

### 2.2 变化来源

可信度的变化只有两类来源：
1. **Review 显式调值**（验证冲突后拉开差距，见第六节）
2. **证据引擎计算**（支持/反对边聚合，见第四节）——实际可信度

> **暂不做**：非冲突可信度变化（来源失信连带压低、推断被否定触发）——首版不做，来源失信靠写入时主观判断（写入者定初值），推断被否定也不自动触发。见 [06-pending-todos.md](06-pending-todos.md)。

### 2.3 实际可信度 vs 锚点

- **锚点 `c⁰`**：写入者定的初值，进公式的 logit 基础项
- **实际可信度 `c_actual`**：锚点 + 证据网络派生的值，用于召回、展示、触发 Review、跨等级判定
- 召回/展示/触发全部用 `c_actual`；锚点只是写入起点

## 三、程度值（strength）

- 连续值 `[-1, +1]`，复用现有字段
- 表达：态度类断言的**方向与强度**（`喜欢 +0.9` = 爱，`喜欢 +0.4` = 喜欢，`喜欢 -0.8` = 不喜欢）
- **替代"拆两个谓词"**（不建"喜欢/讨厌"两个谓词，用同一谓词 + 正负 strength）
- 保留五级快捷语法 `++ / + / 0 / - / --` 映射 1.0 / 0.4 / 0 / -0.4 / -1.0（与情绪模型一致），写入时可提交任意连续值
- **不沿用到 Journal**：Journal 是正文叙事，程度靠文字表达（Journal 无 strength）

## 四、证据网络（支持/反对边）

### 4.1 支持/反对边 = 断言引用断言

"断言 Sᵢ 支持/反对 A" 这件事**本身是一条断言** `Cᵢ`：

```
Claims: { subject: {type: assertion, ref: 断言Sᵢ},
          predicate: {type: relation, index: "支持"},
          object: {type: assertion, ref: 断言A},
          strength: +0.8 (支持) / -0.7 (反对),
          Credibility: 0.8 }   -- "这条支持关系本身多可信"
```

- **"支持"是特殊关系谓词**：涉及可信度计算，subject/object 均为 assertion 类型
- **反对 = 支持 + 负 strength**：不单独建"反驳"谓词
- 支持边自身的 `Credibility`：万一"这两条其实不冲突/关系不成立"，支持边可信度低 → 搬运质量缩水，自愈
- 它与其他断言一样有锚点、可被 Review 改、可被证据网络影响

### 4.2 证据强度

对断言 A，每条影响它的边贡献：

```
e_i = c_Sᵢ × c_Cᵢ × sᵢ
```

- `c_Sᵢ`：支持者自身的**实际可信度**（递归，见 4.5）
- `c_Cᵢ`：这条支持/反对关系断言本身的可信度
- `sᵢ ∈ [-1, +1]`：态度强度（strength），正=支持、负=反对

三者任一差，这条证据贡献就小；但权重压低只是"贡献小"，不会变成负数伤害 A。

分组：
- 支持组 `P = {eᵢ | eᵢ > 0}`
- 反对组 `N = {|eⱼ| | eⱼ < 0}`

### 4.3 组内聚合（noisy-OR，质量 > 数量）

```
Support(A) = 1 - ∏_{i∈P} (1 - eᵢ)
Oppose(A)  = 1 - ∏_{j∈N} (1 - eⱼ)
```

展开理解：
```
Support = e₁ + (1-e₁)e₂ + (1-e₁)(1-e₂)e₃ + ...
```
- 最强证据几乎全额计入；后续证据只在"剩余空间"里产生边际效果
- 100 条弱支持（e=0.01）打不过 1 条强支持（e=0.9）：1-(0.99)^100 ≈ 0.63 < 0.9 —— 质量优势保住了
- 单调不减：新增支持（再弱）都不会让 Support 变小 → 弱支持绝不带来负面影响

### 4.4 融合（logit + sigmoid，天然有界）

```
L_A = logit(c_A⁰) + k_sup · Support(A) - k_opp · Oppose(A)
c_A_actual = σ(L_A) = 1 / (1 + e^(-L_A))
```

- `c_A⁰`：A 的锚点（写入者初值）
- `k_sup, k_opp`：调节系数（约 2~4），控制"最多能把 logit 拉多远"
- **`σ` 值域天然 (0,1)** —— "实际可信度不超过 1"由公式结构保证，无需额外 clip

### 4.5 递归依赖（传播）

- A 依赖 B，B 可能依赖 A（环）
- 处理：**迭代 + 深度限制**（不专门做环检测/拓扑排序；有环就迭代到限制轮数截断）
  1. 初始化：所有 `c_actual ← c⁰`
  2. 迭代：按上式重算，邻居用上一轮值
  3. 加阻尼（如 `c⁽ᵗ⁺¹⁾ = 0.85·c_new + 0.15·c⁽ᵗ⁾`）保证收敛
  4. 迭代到变化 < 阈值（如 1e-4）或固定轮数（如 20 轮）停止
- 第一版**全量迭代**即可，规模变大后再做环检测/拓扑序优化（YAGNI）

### 4.6 跨等级碾压

stated 与 inferred 冲突：
- **等级决定**，与数字无关——任何 stated 直接否定 inferred
- **自动处理，不建冲突工单**（碾压是确定的，Review 只处理同等级对决）
- 落值：inferred 直接压到 ~0（保证碾压后该槽位自动 ≤1，不再触发 Review）

## 五、冲突组

### 5.1 结构（单独建库）

```
ConflictGroups
├── Id
├── SubjectKey / PredicateKey     -- 冲突槽位（subject + 排他属性名）
├── Reason                         -- 检测原因
├── DetectedAt / ResolvedAt? / ResolvedBy?
└── Members → ConflictGroupMembers

ConflictGroupMembers
├── GroupId
├── ClaimId
└── JoinAt
```

- **无 status 字段**——状态全由数值派生（见 5.3）
- 表只存成员关系 + 审计时间戳

### 5.2 检测与入组

- **触发**：写入新断言，与已有断言同（subject + 排他属性）槽位取值不同 → **两个就建组**
- 排他属性 = 属性关键词条目带 `IsExclusive=true`（放在 Keywords 上）
- 后来的冲突断言**加入现有组**（"冲突可能发生在组内，两个就建组可以"）

### 5.3 组内约束：总和 ≤ 1

- **同组全部成员 `c_actual` 之和 ≤ 1，恒定成立（解决后也成立）**
- **多方冲突（同组 >2 断言）同样适用，无额外分配策略**——各方瓜分这 1.0 预算，多断言也是和 ≤1，静置靠 Review 拉开差距
- 这意味着"支持"搬运进组的质量不能把组顶爆——超了就是预算不一致，见触发
- **可信度是对"该槽位真值"的质量分配**：一个排他属性（颜色）的真值只有一种正确描述，冲突各方瓜分这 1.0 的信念

### 5.4 触发 Review

**一旦组内 `c_actual` 总和 > 1 → 触发 Review 解决**。

注意：写断言本身不触发，只有"有效质量顶破预算"才触发。

## 六、Review 验证流程

### 6.0 Review 工作流（队列 + 暂存区 + git 式提交）

**Review 是 session**（复用 RuntimeSession，三件套持久化），消费**持久化的待验证队列**（ReviewQueue），改动经**暂存区 + 显式提交**落库。

```
ReviewQueue（待验证队列，持久化表）——唯一的 Review 工作源
├── Id
├── TargetRef                     -- 目标：断言Id / 消息Id / 冲突组Id / JournalId
├── TargetKind: Claim|Message|ConflictGroup|Journal
├── Reason                         -- 为什么进队列（排他冲突/悬空推断/手动标记/支持链矛盾）
├── Source: Conflict|Dream|Manual|Framework
├── Priority: Low|Normal|High
├── Status: Pending|UnderReview|Done|Dropped
├── CreatedAt / ClaimedAt? / DoneAt?
└── ResultRef?                    -- 处理结果关联（可选）
```

- **统一框架**：所有来源都进这一个队列（冲突组超预算自动入队、Dream 发现入队、手动 mark 入队）。冲突组退化为**纯数值约束** + 队列的一个 Source，不再直接是"Review 候选"
- **崩溃恢复**：`Status=UnderReview` 的项重启后重置回 `Pending`（保留 `InterruptedAt` 时间戳），Review 重新认领——最多重做一项，不丢工作

### Review 触发（队列有活即激活，非轮询）

```
冲突组超预算 / Dream 发现 / 手动 mark
  → 入队（ReviewQueue, Source 区分）
  → 全局开关开着 + 队列有活 → 启动 review session（自动按需）
  → 按 Priority 认领【单个】项（High > Normal > Low）
  → 查证 → 调锚点进暂存区 → preview 预览 → commit 提交
  → 队列空 → review 退出
```

- **按需激活**：队列有活才启动，不等轮询；处理完队列空即退出
- **一次认领一个**：专注解决单个问题，不贪多（批大小 = 1）
- **优先级**：High（冲突组超预算）> Normal > Low，按 Priority 认领
- **总开关分级**：
  - **全局开关** `ReviewConfig.Enabled`：关掉后 Review 不激活（冲突照常入队记账，只是不自动处理）
  - **单次手动强制**：管理员需要时手动触发一次 review（对应旧 `force-review`，可续跑不清进度）
- **开关管激活、不管入队**：关了开关冲突照样入队，不丢待办，只是不自动处理

```
Review session 处理队列项
  ├─ 每项处理 → 改动进【暂存区】（不落库）
  ├─ 预览：模型调 review_preview，看"如果合并了，我的改动会导致什么"
  ├─ 模型满意 → review_commit（显式提交，落库 + 重算）
  ├─ 不满意 → 调整暂存区 → 再预览 → 再提交
  └─ review_complete → 强制提交剩余暂存 + 队列收尾
```

- **暂存区持久化**：`Status=UnderReview` 项 + 暂存区随 review session 持久化（state.json），崩溃不丢未提交工作
- **预览（git diff 式）**：模型对暂存区调 `review_preview` → 引擎构造**临时 batch**（暂存改动 + 现有证据边），跑 EvidenceEngine 只算**不写库**，输出"改动会导致哪些 c_actual 变动、哪些冲突组超预算"——**先看影响再决定**，避免盲改
- **提交 = 原子事务**：全部暂存改动落库 + EvidenceEngine 重算 c_actual + 校验组内和 ≤1

**Review 工具链**（进 `review_*` 系列）：
- `review_preview` — 预览暂存区改动的可信度影响（dry-run，不写库）
- `review_commit` — 显式提交暂存区（原子事务落库 + 重算 + 校验）
- `review_list_queue` — 查看待验证队列
- `review_resolve` — 认领/处理队列项（调锚点 → 进暂存区）

### 6.1 目标：拉开可信度差距

Review 的目的**不是"A 赢了 B 输了"**，而是：

> "A 的可信度调到 x，B 的可信度调到 x，检查是否修复完毕，通过，完成。"

结果全由可信度分配表达，**无四态枚举**：

| 场景 | 可信度分配（示例） |
|---|---|
| 一真一假 | 胜者 ≈0.9 / 败者 ≈0.05 |
| 合并（其实不排他） | 冲突是误标 → 解除排他 / 拆组，双方各取质量，不再共享预算 |
| 全假 | 都压到 ~0.1，预算近乎空置（"没人知道真相"） |
| 未解决 | 质量摊开、和 ≤1，静置——直到新证据把预算顶爆 |

### 6.2 归一化 = 最后手段

**默认不自动归一化**。数值约束由公式结构保证；归一化只在 Review 决定用——"没有找到任何实际有用的证据，纯为了消冲突的最后手段"。

归一化是**等比缩放**（保留相对差距），作用后组内和 ≤1-ε，冲突记录仍保留（供审计/后续澄清），不代表冲突已解决。

### 6.3 流程

```
写入 → 触发冲突检测 → 建组（或入组）→ 证据引擎重算 c_actual
  └─ 组内和 >1 ──→ 自动产生 ReviewQueue 项（Source=Conflict）
       └─ Review session 认领（ReviewQueue）→ 查证 → 调锚点进暂存区
            ├─ review_preview 看影响 → review_commit 提交
            ├─ 重算 c_actual → 检查组内和是否修复（≤1）
            └─ 通过，完成。组标 ResolvedAt，队列项 Done。
```

## 七、与旧设计的关系

- **取代"反驳"谓词**：跨断言否定 = `支持 + 负 strength`；结构性冲突 = 冲突组。无独立"反驳"谓词
- **取代"矛盾的表达"（01 旧章节）**：不再自动生成 `B 反驳 A` 断言；改为冲突组 + 可信度
- **取代旧信标的自动生成部分**：框架自动验证信号 = 冲突组超预算；工作端手动 `mark_for_review` 保留
- **推翻 9.2"无 confidence 字段"**：可信度存于断言内，且是显式过程产物（写入者锚点 + 验证调值），不是系统凭空猜——**体系性修正，见 01 更新**

## 八、关键性质小结

1. **支持只增不减**：新增支持不会让 Support 变小
2. **反对只减不增**：新增反对不会让 Support 变大
3. **质量 > 数量**：强证据主导，弱证据边际
4. **天然有界**：sigmoid 输出 ∈ (0,1)，无需 clip
5. **组内和 ≤1 恒定**：冲突各方瓜分信念预算，解决后也成立
6. **强度与可信度正交**：`爱+0.9` 可以是低可信
7. **Review 拉开差距**：语义结果靠可信度分布，无四态枚举
8. **归一化是最后手段**：默认不自动，Review 决策才用
9. **队列统一工作源**：ReviewQueue 是 Review 唯一的待处理清单，冲突组只是其一个 Source
10. **git 式提交**：Review 改动进暂存区，模型 `review_preview` 预览影响后 `review_commit` 显式提交（原子事务 + 重算 + 校验）
